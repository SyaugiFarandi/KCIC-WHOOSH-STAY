### Accommodation Policy Engine: versioned registry, deterministic evaluation, workflow enforcement — 2026-11-23 (Phase C)
- Schema (additive only): migration `20261123170000_policy_engine` extends the existing `accommodation_policies` table in place (new engine columns; `engine_managed` defaults to false so legacy roster-recommendation rows stay outside the engine), creates `accommodation_policy_versions` and `policy_evaluations`; migration `20261123180000_reservation_policy_context` adds `is_emergency`, `emergency_reason` and `priority` (default `NORMAL`) to `reservations`. No column, table or row was dropped or renamed; applied to the dev, test and E2E databases.
- Permissions: additive `policies.read`, `policies.create`, `policies.update`, `policies.activate`, `policies.manage` and `policies.evaluate` (registry 71 codes, seed `rolePermissions=240`). SYSTEM_ADMIN holds all six; DORMITORY_MANAGER/ADMIN and FRONT_DESK read + simulate; AUDITOR read-only; CREW has no access. Dev database synced with `SEED_DEMO=false db:seed` (RBAC upsert only; users/data untouched).
- Registry lifecycle: creation produces DRAFT v1 unapproved; every edit writes version n+1 with optimistic `expectedVersion` (`409 POLICY_VERSION_CONFLICT` on stale writes), resets approval and leaves the policy inactive. Approval (`policies.manage`, note ≥3 chars) is separate from activation (`policies.activate`), which requires an approved, non-expired version; ACTIVE policies must be deactivated before deletion (`409 POLICY_STATE_INVALID`). All writes are audited.
- Deterministic engine: 16 categories with configurable parameters (no official KCIC values invented; the UI marks example values as illustrative). Precedence is `DENIED > REQUIRES_MANUAL_REVIEW > REQUIRES_APPROVAL > ALLOWED` regardless of priority, ties broken by priority desc then code asc; inclusive effective dates, dormitory scope, exact-match conditions, and per-category workflow scoping so unrelated flows stay ALLOWED.
- Workflow integration: reservation create (automatic/manual, emergency, priority), cancellation and check-in evaluate the engine. Decisions return the blocking policy id/code/version, reason, conditions and timestamp; every evaluation is logged to `policy_evaluations` (simulations flagged). Violations are recorded in the existing Exception Center with a stable dedupe key (`occurrenceCount` increments, closed rows reopen) — no duplicate rows. On reservation create the violation joins the reservation transaction (`exceptionTx`), so it commits only with approval/manual-review outcomes and rolls back with a DENY, whose audit trail remains in the evaluation log.
- API: `/api/v1/policy-engine` — `GET /summary`, `GET/POST /policies`, `GET/PATCH/DELETE /policies/:id`, `GET /policies/:id/versions`, `POST /policies/:id/approve|activate|deactivate`, `POST /evaluate` (simulation, `policies.evaluate`), `GET /evaluations` (filters + pagination).
- Management UI: `/manage/policies` («Kebijakan Akomodasi», «Pengelolaan Sistem» group, `policies.read` guard) with KPI cards, category/status/dormitory/search filters, registry table, create/edit dialog with JSON parameter and condition editors, detail with version history and permission-gated approve/activate/deactivate/delete, simulation form and evaluation-log tab. Loading, empty, error, permission and disabled states included; every action calls the real API.
- Tests: unit **88/88** (10 files, new `engine.test.ts` covering precedence, ties, effective dates, dormitory/condition scoping, all 16 category evaluators and violation keys); integration **143/143** (24 files, new `policies.test.ts` covering lifecycle, approval gating, RBAC matrix, simulation + logs, effective dates, reservation DENY/approval paths, cancellation and check-in enforcement with exception dedupe); new Playwright `policies.spec.ts` **3/3** (create → approve → activate → deactivate → delete, live simulation + log, crew denial); axe **4/4** with `/manage/policies` added to the 20-route management scan; sidebar reachability pass; root typecheck/lint/build pass.

### Reservation Exception Center: additive conflict queue — 2026-11-23 (Phase B)
- Schema (additive only): new `reservation_exceptions` table via migration `20261123120000_reservation_exceptions` with unique `dedupe_key`, `exception_type`, `severity`, `status`, dormitory plus optional reservation/room/bed links, `evidence` JSON, `occurrence_count`, assignee/acknowledgement, resolver/resolution note and detection timestamps; indexes cover `(status, severity, detected_at)`, `(dormitory_id, status)`, reservation, and `(assigned_to, status)`. No existing table was altered or dropped.
- Permissions: additive `exceptions.read` and `exceptions.manage` (registry now 66 codes, seed `rolePermissions=228`); granted to SYSTEM_ADMIN, DORMITORY_MANAGER, DORMITORY_ADMIN and FRONT_DESK for manage, AUDITOR read-only. Dev database synced with `SEED_DEMO=false db:seed` — RBAC upsert only, existing users/data untouched.
- Conflict generation: reservation create/allocate record `ALLOCATION_CONFLICT` or `OVERBOOKING` before rethrowing the original 409, and check-in records `READINESS_FAILURE` (with failed readiness reasons) or `ALLOCATION_MISSING`. Recording is best-effort (`safeRecordReservationException` logs and swallows failures) so the original response is never masked. Dedupe keys increment `occurrenceCount` on repeats and reopen closed rows as `OPEN` with assignment/resolution cleared.
- API: `GET /api/v1/exceptions` (status/severity/type/dormitory/`assignedToMe`/`openOnly`/`q`, status counts and pagination), `GET /api/v1/exceptions/:id`, `PATCH .../assign` (self, another active user, or unassign) and `PATCH .../resolve|dismiss` (mandatory note). Scope is enforced server-side: list is limited to accessible dormitories, out-of-scope detail returns 404, `SELF` principals 403. Invalid transitions return `409 EXCEPTION_STATE_INVALID`; assign/resolve are audited.
- Management UI: `/manage/exceptions` («Pusat Eksepsi Reservasi», Operasional group, `exceptions.read` guard) with open/acknowledged/critical/resolved KPI cards, status/severity/type/dormitory/assignee filters and search, queue table, detail drawer showing evidence, and assign/resolve actions gated by `exceptions.manage`; loading, empty, error and permission states included.
- Tests: unit **63/63** (9 files, 6 new dedupe/schema tests); integration **134/134** (23 files, new `exceptions.test.ts` proving allocation-conflict dedupe, overbooking, readiness failure, missing allocation, scope isolation and the assign/resolve state machine); targeted Playwright `management` + `sidebar-navigation` **13/13**; axe **4/4**; responsive audit **34/34** (all 17 widths, `/manage/exceptions` included); root typecheck/lint/build pass.

### Occupancy Intelligence: canonical capacity, read model, API and management page — 2026-11-23 (Phase A)
- Shared contract: `@whoosh/shared/occupancy.ts` defines `BedOccupancyStatus` (AVAILABLE/RESERVED/OCCUPIED/CLEANING/MAINTENANCE/BLOCKED), summary/trend/forecast query schemas (92-day trend guard), summary/trend/forecast result types, Indonesian status labels and the four published formulas. Additive permission `occupancy.read` (permission registry now 64 codes) granted to DORMITORY_MANAGER, DORMITORY_ADMIN, FRONT_DESK and AUDITOR (SYSTEM_ADMIN inherits); not granted to CREW, HOUSEKEEPING or MAINTENANCE. Seed remains idempotent (`permissions=64`, `rolePermissions=219`); the dev database was synced with `SEED_DEMO=false db:seed`, which upserts RBAC only and leaves users/operational data untouched.
- Canonical capacity: new `capacityBedWhere` helper (BED ACTIVE in ROOM ACTIVE in BUILDING ACTIVE in DORMITORY ACTIVE, within `AccessScope`). Dashboard `totalBeds`, calendar, occupancy and report capacity, and availability now share it; out-of-service beds (maintenance/blocked/inactive room or bed) are counted separately and excluded from capacity. Integration test proves dashboard = occupancy = calendar = report.
- Occupancy API: `GET /api/v1/occupancy/summary|trend|forecast` behind `occupancy.read`; filters by date, dormitory, building, floor, room; scope-aware dormitory/building predicates; `selfOnly` and out-of-scope ids return 403; invalid/impossible dates (e.g. `2026-02-31`) and reversed or >92-day ranges return 400. Status precedence BLOCKED > MAINTENANCE > OCCUPIED > RESERVED > CLEANING > AVAILABLE; allocation overlap is inclusive-start/exclusive-end; inventory blocks use timestamptz overlap; open housekeeping tasks mark CLEANING. `occupancyRate` is `null` when capacity is 0. Forecast declares its basis (`CONFIRMED_ONLY` or `ROSTER_INCLUDED` where roster recommendations exist), confidence (HIGH/MEDIUM/LOW) and returns `INSUFFICIENT_DATA` with null projections when capacity is 0 — no statistical model or synthetic values are implied.
- Management UI: `/manage/occupancy` («Inteligensi Hunian» in the Reservasi group, `occupancy.read` route guard) with date + cascading dormitory/building/floor/room filters, four KPI cards, status distribution, data-quality/formula panel, per-dormitory table, 14-day occupancy trend and a 14-day rule-based forecast table with basis/confidence badges, over-capacity flags and an explicit insufficient-data state. Loading, empty, error and retry states included; no new palette, tokens or duplicate menus.
- Accessibility/responsive: shared `DataTable` scroll regions are now keyboard-focusable (`tabIndex=0`, `role=region`, focus ring); occupancy chart/forecast cards use `min-w-0` so mobile layouts do not overflow. A11y and responsive failures found during verification were fixed, not waived.
- Verification: root typecheck/lint exit 0; production build exit 0; unit **57/57** (8 files, incl. 4 occupancy classifier tests); integration **128/128** (22 files, incl. 6 occupancy tests); targeted Playwright `management` + `sidebar-navigation` **13/13**; axe **4/4**; management responsive audit **all 17 widths 320–2880 pass**; no schema migration, no removed API, no RBAC removal.
