# UI/UX Guidelines — Whoosh Stay

## 1. Experience strategy

Whoosh Stay has two intentionally different experiences:
- **Crew Portal:** premium hospitality, easy discovery and booking.
- **Management Portal:** efficient enterprise operations, dense data, clear status and workflow control.

Both share brand tokens, typography, components, accessibility and responsive behavior. Do not force the crew experience into an admin dashboard layout.

## 2. Brand and visual direction

- Product identity: WHOOSH STAY.
- Visual personality: modern, calm, trustworthy, premium, operationally clear.
- Primary brand direction: deep red/maroon inspired by KCIC identity, balanced with warm neutrals.
- Crew Portal: warm off-white or muted neutral surfaces, quality accommodation photography, restrained accent color, clear booking CTA.
- Management Portal: charcoal/neutral or warm gray surfaces, compact red-accent sidebar, high information clarity.
- Avoid generic AI-generated dashboard appearance, excessive gradients, unnecessary glassmorphism, oversized cards and decorative charts.
- Do not use plain white as the only visual treatment for every page.

## 3. Typography and layout
- Use a consistent readable sans-serif such as Inter or Plus Jakarta Sans.
- Use a spacing scale (4/8/12/16/24/32).
- Desktop content max width should be intentional; tables may use full width.
- Sidebar should be compact, collapsible and role-aware.
- Use consistent page title, breadcrumb, action area and content hierarchy.
- Tables default to 10–15 rows with server pagination.
- Maintain visible focus, keyboard support and sufficient contrast.

## 4. Crew Portal navigation

Top navigation or compact mobile navigation:
- Beranda
- Cari Penginapan
- Reservasi Saya
- Jadwal Menginap
- Bantuan / Profil

### Crew home page
- Greeting and upcoming duty/stay context where available.
- Prominent search module: location/station, check-in, check-out, occupants.
- Recommended internal dormitories only.
- Upcoming reservation card.
- Booking status timeline.
- Clear empty state when no recommendations exist.

### Search results
- Filter by location, date, capacity, room type and facilities.
- Cards show dormitory name, location, photo, room type, capacity and available bed count.
- Do not display a room as available until backend availability result confirms it.
- Include sort controls that are meaningful: availability, location relevance, capacity.
- Show no-results explanation and alternate date/location suggestions.

### Property/room detail
- Photo gallery with real uploaded images or clearly labeled demo assets.
- Facilities and room rules.
- Room/bed capacity and availability.
- Check-in/check-out instructions.
- Reservation policy summary.
- Booking CTA with date/occupant summary.

### Booking flow
- Review employee/guest details.
- Confirm stay dates.
- Show room/bed allocation policy.
- Show approval status expectation.
- Submit with clear loading, success and failure states.
- Never imply confirmation if the booking is only pending approval.

### My reservations
- Tabs/filters: Upcoming, Pending, Active, Completed, Cancelled.
- Booking detail with status timeline.
- QR shown only when eligible and generated by backend.
- Cancellation action only when allowed.

## 6. Management page patterns

- Dashboard: KPI strip, date/location filters, arrivals/departures, occupancy visualization, pending queue, exceptions.
- List page: title, concise description, primary action, search/filter toolbar, table, pagination.
- Detail page: summary header, status badge, tabs for details/history/attachments.
- Form: grouped fields, inline validation, save/cancel, unsaved-change handling.
- Approval: review context, policy explanation, approve/reject with reason.
- Calendar: date navigation, occupancy states, accessible legend and list alternative.
- Room map: building/floor/room hierarchy with bed-level state.
- Housekeeping: task queue with assignment and checklist.
- Maintenance: priority, blocked inventory indicator, evidence and resolution workflow.

## 7. Status design

Use consistent semantic status labels:
- Available / Tersedia
- Occupied / Terisi
- Reserved / Dipesan
- Pending Approval / Menunggu Persetujuan
- Checked In / Sedang Menginap
- Checked Out / Selesai
- Cleaning / Dibersihkan
- Inspection Required / Perlu Pemeriksaan
- Maintenance / Dalam Perbaikan
- Blocked / Diblokir
- Cancelled / Dibatalkan
- Rejected / Ditolak

Never rely on color alone; include text and accessible icon/label.

## 8. Responsive behavior
- Desktop: full management sidebar and data tables.
- Tablet: compact/collapsible sidebar; tables may scroll or switch to cards.
- Mobile: bottom/top navigation for crew; management tasks prioritized with compact navigation and stacked data.
- Booking and QR workflows must be mobile-first.
- Avoid horizontal page overflow.

## 9. Interaction and quality
- Every visible action must work or be explicitly disabled with an explanation.
- No dead links, placeholder buttons or fake success messages.
- Include loading, empty, error, permission-denied and offline/integration-unavailable states.
- Confirm destructive or consequential actions.
- Preserve filters when navigating back from detail.
- Use optimistic updates only where rollback and consistency are safe.
- Provide keyboard access and focus management for dialogs.
- Use skeletons for loading, not layout shifts.

## 10. Content and language
- Initial UI language: Indonesian.
- Keep code identifiers and API names in English.
- Use consistent terms: Reservasi, Dormitory, Kamar, Tempat Tidur, Check-in, Check-out, Okupansi, Alokasi.
- Use realistic demo data labeled DEMO; do not invent actual KCIC dormitory names or locations.
